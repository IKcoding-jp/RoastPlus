# DESIGN.md 整備デザイン仕様

作成日: 2026-05-17
対象: `DESIGN.md`

## 目的

RoastPlus の `DESIGN.md` を、単なる実装済みスタイルの棚卸しではなく、ページ別のデザイン一貫性を保つための判断基準として整備する。

特に重視することは、ページごとに見た目や操作位置がばらつかないこと。新しい画面を作るとき、既存画面を直すとき、実装者が「このページタイプならこの構成」と判断できる状態を目指す。

## デザインコンセプト

RoastPlus のデザインコンセプトは次の通り。

> 現場で迷わない業務PWA。コーヒーらしさは、操作を邪魔しないアクセントとして効かせる。

主軸は「現場オペレーション重視」とする。明るく、読みやすく、押しやすく、日常業務で迷わないことを優先する。

コーヒーらしさは、ブランド色、テーマ、タイマー、カードヘッダー、限定的な演出で表現する。すべての画面を濃いブラウンや強い装飾で覆う方向にはしない。

## デザイン原則

優先順位は次の順に固定する。

1. 現場で迷わない
   - 画面を開いた瞬間に、今の状態と次の操作が分かる。
   - 説明文を増やすより、配置とラベルで理解できる状態を優先する。

2. ページごとの型を揃える
   - 同じ目的の画面は、ヘッダー、余白、最大幅、主要アクション位置、空状態の出し方を揃える。
   - ページ単位で独自デザインを作り続けない。

3. モバイルで押しやすい
   - スマートフォン、タブレット、PWA利用を前提にする。
   - タッチ領域は原則 44px 以上を確保する。

4. 情報が一目で読める
   - 時間、担当、状態、次アクションは本文より強く見せる。
   - 一覧カードは 1カード1主題を基本にする。

5. コーヒーらしさは控えめに効かせる
   - コーヒーらしい色や演出は、業務理解を邪魔しない範囲で使う。
   - 集中操作画面やホームでは少し強めてもよい。

6. 毎日使って疲れない
   - 強いアニメーション、過度なグラデーション、重い装飾は限定する。
   - 長時間使う一覧、フォーム、設定では落ち着いた表現を優先する。

## ページタイプ別ルール

`DESIGN.md` の中心には、次の6つのページタイプを置く。

各ページタイプには、主な用途、対象ページ例、推奨レイアウト、ヘッダー、最大幅、主要アクション位置、使う共通UI、避けることを表で記載する。

### 1. ホーム / ハブ

目的は、機能選択を迷わせないこと。

対象例:
- ホーム

基本方針:
- ブランドヘッダーを使う。
- 2列中心の機能カードで、次に開く機能を選びやすくする。
- ラベルは短く、説明文は最小限にする。
- カード内の情報量を増やしすぎない。

### 2. 一覧 / 管理

目的は、データを探す、追加する、編集すること。

対象例:
- 担当表
- スケジュール
- 欠点豆
- 作業進捗
- 試飲一覧
- 通知一覧

基本方針:
- 上部にタイトルと主要アクションを置く。
- 検索、絞り込み、ソートは近い場所に集約する。
- モバイルはカード、広い画面はテーブルやグリッドを使ってよい。
- 空状態では、次に押すボタンを出す。

### 3. フォーム / 編集

目的は、入力ミスを減らして保存すること。

対象例:
- レシピ作成、編集
- 試飲セッション作成、編集
- 設定入力
- お問い合わせ

基本方針:
- `max-w-2xl` または `max-w-lg` を基本にする。
- 入力欄は縦積みを基本にする。
- 保存ボタンは下部、右下、または固定フッターのいずれかに揃える。
- 削除などの危険操作は通常操作から離し、Danger Zone として分離する。

### 4. 集中操作 / 実行

目的は、作業中に状態と次操作だけを見ること。

対象例:
- ローストタイマー
- ドリップガイド実行
- クイズ実行
- 時計

基本方針:
- 画面固定または準固定のレイアウトを使う。
- 中央に主要状態を置く。
- 下部に操作をまとめる。
- 余計なカードや説明を減らす。
- コーヒーらしい演出はこのタイプで強めてもよい。

### 5. 詳細 / 参照

目的は、内容を読む、判断材料を見ること。

対象例:
- 欠点豆詳細
- 開発秘話
- 規約、プライバシーポリシー
- 履歴詳細

基本方針:
- `max-w-3xl` 前後を基本にする。
- 見出し階層を明確にする。
- 画像や本文を読みやすく配置する。
- 操作より読解を優先する。

### 6. モーダル / 確認

目的は、短い判断、設定、確認を完了すること。

対象例:
- 削除確認
- フィルター設定
- OCR確認
- 詳細設定

基本方針:
- 背景は `bg-overlay` を必須にする。
- 幅は `max-w-sm` から `max-w-md` を基本にする。
- ボタンはキャンセル、実行の順にする。
- 危険操作は `danger` を使う。
- 長い内容や複雑な設定は、モーダルではなくページ化を検討する。

## ページ間で揃える共通ルール

### ヘッダー

- 通常ページは `FloatingNav` とページタイトルを基本にする。
- クイズやタイマーなど集中画面は、固定ヘッダーや最小ナビでもよい。
- ホームだけはブランドヘッダーを使う。
- タイトル文言は短くする。
- 説明文をヘッダー内に増やしすぎない。

### 主要アクション

- 「追加」「保存」「開始」など主操作は1画面に1つを目立たせる。
- 補助操作は `secondary`、`ghost`、`outline` に落とす。
- 危険操作は通常操作から距離を取り、`danger` で明確にする。
- モバイルでは、主要アクションを上部右側、下部固定、またはカード末尾のいずれかに揃える。

### 空状態

- 空状態は `EmptyState` または `Card variant="guide"` を基本にする。
- 「何もありません」だけで終わらせない。
- アイコン、短い見出し、1行説明、主要アクションの順に揃える。

### エラー・警告

- エラーは赤、警告は黄、成功は緑、情報はシアンのセマンティック色を使う。
- 長文エラーは避け、ユーザーが次に何をすればよいかを書く。
- 本番影響や削除操作は確認ダイアログを挟む。

### カード密度

- 一覧カードは 1カード1主題にする。
- ホームカードやダッシュボードカードは短くする。
- 詳細ページで情報を広げる。
- カードの入れ子は禁止する。必要ならセクション分けにする。

## 実装リファレンスの構成

既存の `DESIGN.md` にあるカラー、余白、角丸、コンポーネント、禁止事項は残す。ただし、単なる一覧ではなく「いつ使うか」が分かる順番に整理する。

### カラー

- セマンティックトークンを必ず使う。
- `bg-page`, `bg-surface`, `bg-overlay`, `text-ink`, `border-edge`, `bg-spot` などを主要トークンとして整理する。
- `bg-white`, `text-gray-*`, `border-gray-*` などのハードコード色は禁止する。
- ブランド固定色は例外的に使う色として扱い、通常画面ではトークン優先にする。

### タイポグラフィ

- ページタイトル、セクション見出し、本文、補助文、数値表示の型を定義する。
- タイマーや大きな数値以外で `text-4xl` 以上を乱用しない。

### 余白・最大幅

- モバイルは `px-4` を基本にする。
- 標準ページは `max-w-4xl` を基本にする。
- フォームは `max-w-2xl` または `max-w-lg` を基本にする。
- 詳細読み物は `max-w-3xl` を基本にする。
- ページタイプ別ルールと対応させる。

### コンポーネント

- `components/ui` の使用を必須にする。
- `Button`, `Card`, `Input`, `Modal`, `Dialog`, `Tabs`, `EmptyState`, `FloatingNav` を、Props一覧より使い分け判断を優先して整理する。

### アニメーション

- 業務画面は控えめにする。
- 集中画面やホームだけ少し強めてもよい。
- `prefers-reduced-motion` を尊重する。
- 装飾アニメーションで操作理解を邪魔しない。

### 禁止事項

- ハードコード色
- 生Tailwindボタン、カード、入力
- テーマ名の直接判定
- モーダル背景の `bg-surface`
- カードの入れ子
- 目的のないグラデーションや過度な装飾

## スコープ

今回の整備対象は `DESIGN.md` の内容整理と明文化に限定する。

この仕様では、実アプリの画面デザイン変更、共通UIコンポーネントの実装変更、CSS変数の追加、依存関係追加は行わない。

## 未決定ではない事項

- 主軸は「現場オペレーション重視」
- コーヒーらしさはアクセント
- `DESIGN.md` は「方針 + 実装ルール」の二層構成
- ページ別の一貫性を中心にする
- ページタイプは6分類

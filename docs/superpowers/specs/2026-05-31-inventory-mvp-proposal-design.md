# 在庫・不足品 提案用MVP 設計仕様

- **作成日**: 2026-05-31
- **ステータス**: ドラフト（ユーザーレビュー待ち）
- **位置づけ**: **提案・検証用MVP**。本番投入を前提とせず、フィーチャーブランチ `feat/inventory-mvp-proposal` で試作する。**main にはマージしない**。本社/管理者に実物を見せ、「在庫・不足品をExcelで管理するか、RoastPlusで管理するか」の意思決定材料にする。採用されれば本番化、されなければブランチごと破棄。

---

## 1. 目的と背景

### 1.1 目的
現場の誰もが「これ足りない」をその場でスマホから挙げられ、不足品が一覧に集まる体験を**動く実物**で示す。Excel管理かアプリ管理かの判断を後押しする提案材料を作る。

### 1.2 背景（現状 As-Is）
現場ヒアリング（2026-05-31）で判明した現状：

- 在庫は**記録せず、棚を目視**して「足りてる/足りてない」を確認している。
- 不足品は**ホワイトボードや紙にメモ**している。
- 発注は**本社の人**に、会社のスマホから連絡してお願いする（**現場は発注しない**）。
- **明日から管理者がExcelで管理するかもしれない**が、**未定**。RoastPlus側で管理できるようになる可能性もある。

### 1.3 なぜ「提案用MVP」か
- 発注主体が本社（アプリ外）で、更新運用も未確定。この段階で本番投入すると、Excelとの**二重管理**や「運用が無い機能」になり、過去に削除した5機能と同じ失敗を招く。
- 一方、現場の誰もがその場でスマホから不足品を挙げられる点は、Excel（管理者/PCが要る）にもホワイトボード（その場でしか書けない・消える）にも出せない**アプリ固有の価値**。これを実物で見せて判断を仰ぐのが最も合理的。

## 2. このMVPで検証/提案したい問い（成功条件）

提案の場で、以下が「伝わる／確かめられる」ことを成功とする。

- [ ] 現場スタッフが、棚の前で**1〜2タップ**で不足品を挙げられる（紙・ホワイトボードより速いと感じる）。
- [ ] 挙がった不足品が**1つの一覧（要発注リスト）に集まり**、本社に伝える内容が明確になる。
- [ ] 管理者/本社が、対応した品目を**「対応済み」にして一覧から消せる**（やりとりの完結が見える）。
- [ ] 「これならExcelやホワイトボードより良い／このまま運用に乗せたい」という感触が、関係者から得られるか。

> 提案の目的は「完璧な在庫管理」ではなく「**現場発の不足品伝達がアプリで成立するか**」の検証。

## 3. 対象ユーザー

- **主**: 現場スタッフ8名（不足品を挙げる側）。スマホ/iPad、IT習熟度 低〜中。
- **副（提案で想定）**: 管理者（挙がった不足品を確認し、本社に発注を依頼、対応済みにする）。本社がアプリを使うかは本採用時の論点（§9）。

## 4. As-Is 業務フロー（参考）

```
棚を目視 →「○○が少ない」と気づく → ホワイトボード/紙にメモ
   → （誰かが）会社のスマホで本社に連絡 → 本社が発注 → 入荷
```

このフローの「気づく→メモ→伝える」をアプリ化するのがMVPの射程。「本社が発注」はアプリ外のまま。

## 5. MVPの核（To-Be）

信号機方式をベースに、**現場発の不足品伝達**として構成する。

### 5.1 共有在庫/品目リスト
- 品目ごとに信号機3段階：🟢 十分 / 🟡 少ない / 🔴 切れた。
- **1タップで更新**（数量入力なし・棚卸し不要）。
- 「最終更新者・時刻」を表示（誰が挙げたか分かる）。

### 5.2 要発注リスト（自動生成・導出）
- 🟡🔴の品目が自動で集まる（独立データは持たず status から導出）。
- 管理者/本社対応を想定し、`[対応済みにする]` で 🟢 に戻り一覧から消える（本採用時に「誰が押すか」の運用を決める。§10）。

### 5.3 要発注バッジ
- ホーム/ナビに「要発注 (N)」を常時表示（🟡🔴の件数）。アプリを開けば目に入る。

### 5.4 状態遷移
```
十分 ──(消費)──▶ 少ない ──(消費)──▶ 切れた
  ▲                                      │
  └──────────[対応済みにする]────────────┘
```

## 6. 受け入れ条件

- [ ] 品目を追加・編集・削除できる。
- [ ] ステータスを1タップで 十分/少ない/切れた に変更でき、最終更新者・時刻が記録・表示される。
- [ ] 🟡🔴の品目が要発注リストに自動表示される。
- [ ] `[対応済みにする]` で 🟢 に戻り、要発注リストから消える。
- [ ] ホーム/ナビの「要発注 (N)」バッジが件数と一致する。
- [ ] 7テーマで表示が崩れない。
- [ ] デモ用のサンプル品目で、提案の場ですぐ操作を見せられる。

## 7. データ設計

```typescript
interface InventoryItem {
  id: string;
  name: string;                                       // 例: "ドリップ袋"
  category: 'green-bean' | 'material' | 'consumable'; // 生豆 / 資材 / 消耗品（暫定3区分・§10）
  status: 'enough' | 'low' | 'out';                   // 十分 / 少ない / 切れた
  note?: string;                                      // 任意メモ
  updatedBy: string;
  updatedAt: Timestamp;
  createdAt: Timestamp;
}
```

- トップレベル共有コレクション **`inventory`**（1品目 = 1ドキュメント）。
- 要発注リストは status から**導出**（情報を2か所に持たない＝不整合が起きない）。
- **MVP段階のデータ**: 本番Firestoreを汚さないため、デモ用データ／E2Eエミュレータで動かす（本番投入時に方針確定）。

## 8. 認証・認可・Firestore Rules への影響

- 本採用時に必要なルール（案）：`match /inventory/{itemId} { allow read, write: if request.auth != null; }`。これは「認証済み全員が**書き込める**トップレベル共有」で**このプロジェクト初**のパターン（既存 `defectBeans` は読み取り専用）。
- **MVP段階では本番 Rules をデプロイしない**。本採用が決まった時点で、誤削除リスク・owner isolation 例外の妥当性を含め**改めてセキュリティレビュー**を行う。
- 過去にルート直下の `teams`/`members` 等が `if false` で無効化された経緯（トップレベル共有を試みてやめた可能性）も、本採用前に確認する。

## 9. Cloud Functions への影響

なし。

## 10. やらないこと（MVPスコープ外・YAGNI）

- 本番デプロイ・本番 Rules 適用（本採用判断後）
- 本社側の専用画面・本社システムとの連携
- Excel との同期・インポート/エクスポート
- 正確な数量管理（〜kg/枚）、消費ペース算出、生産記録v1との連動
- 発注先・発注履歴・金額、プッシュ通知
- 編集権限の制御（MVPは全員編集可）

## 11. 未決事項（本採用が見えてから確定）

1. **更新運用**：状態を誰がいつ更新するか（現状「未定」）。本採用時に現場・管理者と決める。MVPでは「現場の誰でも随時」で仮置き。
2. **「対応済み」を誰が押すか**：管理者か、挙げた本人か。本社がアプリを見るか。
3. **Excel管理になるか／アプリ管理になるか**：本提案の結果次第。
4. カテゴリ3区分（生豆/資材/消耗品）の妥当性、品目の実体・数。
5. 削除方式（物理 or 論理）、`updatedBy` の表示（表示名/メール/uid）、メモ欄の要否。

## 12. 検証方法

- **ユニットテスト** (`npm run test:run`)：status→要発注リスト導出、状態遷移、バッジ件数集計。
- **ページ統合テスト**（vitest + jsdom、Firestoreモック）：ステータス変更→一覧反映、各操作の配線。
- **手動/デモ**：サンプル品目でMVPの一連の操作を実演（提案の場で見せる用）。7テーマ表示確認。
- ローカル検証：`npm run build && npm run test:run`、コミット前に `npm run format:check`。
- 本番 Rules テスト・本番デプロイは本採用判断後に実施。

## 13. 提案後の分岐

- **採用**：本番要件（更新運用・本番Rules・セキュリティレビュー・本社連携）を固め、main へ統合する spec を別途起こす。
- **不採用**：`feat/inventory-mvp-proposal` ブランチを破棄。main は無汚染のまま。

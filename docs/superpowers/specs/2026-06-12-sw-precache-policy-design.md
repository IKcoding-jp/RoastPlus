# SWプリキャッシュ方針の決定とキャッシュ運用ルールの整備（Issue #512）

日付: 2026-06-12
ステータス: 実装済み

## 背景

Service Worker のプリキャッシュ対象が6URLのみで主要業務ページが含まれておらず、「未訪問ページをオフラインで開く必要があるか」が未決定だった。また `CACHE_NAME = v6` / `RUNTIME_CACHE = v7` と番号が不一致で、バージョン運用ルールも明文化されていなかった。

## 決定

**プリキャッシュは現状維持（最小アプリシェルのみ）とし、未訪問ページのオフライン表示は保証しない。**

### 根拠

1. **業務要件**: 現場iPadは常時WiFi接続で、オフラインになることはほとんどない（2026-06-12 ユーザー確認）。オフラインで未訪問ページを開くニーズ自体が存在しない。
2. **技術的制約**: 静的エクスポート＋クライアントレンダリング構成では、HTMLをプリキャッシュしてもページ固有のJSチャンクがなければ未訪問ページは機能しない。完全対応にはビルド時のキャッシュマニフェスト生成（next-pwa / Workbox injectManifest 等）が必要で、ADR-007（カスタム手書きSW採用・next-pwa不使用）と矛盾する。
3. **実態**: 約8名が日常的に使うページは Network First ＋実行時キャッシュ（上限80件）で自然にカバーされる。

## 検討した代替案

| 案 | 内容 | 不採用理由 |
|----|------|-----------|
| 案2 | PRECACHE_URLS に主要業務ページのHTMLを追加 | HTMLだけではJSチャンク不足でオフライン動作せず、効果が見かけ倒しになる |
| 案3 | ビルド時マニフェスト生成（Workbox等）で全アセットをプリキャッシュ | ADR-007と矛盾。常時WiFi前提では費用対効果が見合わない |
| 補足 | sw.js のハッシュスナップショットでバージョン上げ忘れを強制検知 | 編集のたびにスナップショット更新が必要で摩擦が大きい。SW_VERSION一元化＋テスト＋CLAUDE.mdルールで十分と判断 |

## 実装内容

1. `public/sw.js`: `SW_VERSION = 8` を導入し、`CACHE_NAME` / `RUNTIME_CACHE` を導出に変更（番号不一致の構造的防止）。運用ルールとプリキャッシュ方針をコメント化。
2. `lib/pwa/sw.test.ts`: バージョン番号の一致テストと、プリキャッシュ一覧が方針（最小シェル）と一致するテストを追加。
3. `docs/steering/TECH_SPEC.md`: PWAセクションに「プリキャッシュ方針」「キャッシュバージョン運用ルール」を追記。
4. `CLAUDE.md`: SW変更時ルールを `SW_VERSION` 表記に更新。

## スコープ外（やらないこと）

- 更新検知UI（`ServiceWorkerRegistration.tsx`）: install時に `skipWaiting()` 済みで更新停止リスクは低く、現時点では不要。
- SKIP_WAITING メッセージリスナー: 既にコメントアウト済み（将来の更新通知UI実装時の参考として保持）。
